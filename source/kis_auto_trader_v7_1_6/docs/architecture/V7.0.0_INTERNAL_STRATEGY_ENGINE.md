# V7.0.0 내부 Strategy Engine 및 실행 구조

V7.0.0은 V6.0.2의 내부 전략 엔진을 유지하고 실행 책임을 모듈별로 분리한 릴리스입니다. 별도 Strategy Builder 서버는 필요하지 않습니다.

## 실행 구조

- `main.py`: 기존 실행 명령을 유지하는 얇은 호환 진입점입니다.
- `application.py`: 설정 로딩, KIS API/상태/주문/알림 객체 조립, 스레드와 메인 실행 루프, 종료 처리를 담당합니다.
- `trading/buy_process.py`: HTS/Builder 후보 선택, 후보 주문 안전 검증, 주문 직전 최종 게이트 및 공통 `OrderManager` BUY 제출을 담당합니다.
- `trading/sell_process.py`: 일반 포지션 매도 평가/주문 제출과 실시간 청산 이벤트 실행을 담당합니다.
- `trading/fill_handler.py`: WebSocket/REST 체결 이벤트 중복 방지 및 로컬 상태 반영을 담당합니다.
- `trading/orders.py`: 미체결 주문, 불명확 주문, 취소 기록, 체결 누적과 예약 금액의 공통 관리 계층입니다.
- `trading/reconcile.py`: 브로커 잔고 및 미체결 주문 대사를 담당합니다.
- `strategies/` 및 `config/strategies/`: 10개 내부 전략 YAML과 전략 평가기를 보유합니다.

## 매수 안전 순서

1. 전역 신규 매수 게이트(상태 무결성, 거래시간, 매수 일시정지, 일일 거래/손실 한도, 미체결 매수, 포지션 수)를 통과합니다.
2. HTS 조건검색 및/또는 내부 Builder 후보를 평가합니다.
3. 종목 미체결/불명확 주문, 기존 보유 여부, 잔고/주문 대사 안전 상태를 확인합니다.
4. 주문 직전 REST 현재가를 다시 조회하고 주문 방식을 재평가합니다.
5. KIS 주문가능금액과 미체결 매수 예약액을 반영해 수량을 산정합니다. 고정 수량 모드에서도 현금 검증을 생략하지 않습니다.
6. 주문 제출 직전에 종료 신호, KST 진입 시간 및 일일 매수 한도를 다시 검사합니다.
7. BUY는 공통 `OrderManager.submit()`으로 제출합니다. 주문 후 최신 잔고 재대사 전까지 신규 매수를 잠그며, 매도·체결·대사 루프는 계속 실행합니다.

## 전략 설정과 테스트

- 전략 YAML을 변경한 뒤 `./tests/kis_strategy_test.sh --offline --sample-size 10 --seed 42`를 먼저 실행합니다. 이 경로는 첨부 종목 DB에서 무작위 종목코드/이름을 뽑고 합성 OHLCV를 사용하므로 KIS 인증/API를 호출하지 않습니다. 결과 JSON은 `KIS_LOG_DIR`을 따르며 운영 로그와 분리할 수 있습니다.
- 온라인 시세 테스트는 `KIS_PAPER=true`만 허용합니다. 실제 일봉 시세 조회만 수행하고 주문/취소 API는 호출하지 않습니다. 이 감사에서는 온라인 KIS API를 실행하지 않았습니다.
- `python -m pytest -q`, `python smoke_test.py`, `python -m compileall -q .`를 릴리스 검증에 사용합니다.
- YAML의 `enabled: false` 또는 `0`은 해당 기능 비활성화에 사용하고, 선택형 문자열은 `""`로 비활성화할 수 있습니다. 수치 `0`은 필드마다 의미가 다르므로 각 필드 주석과 검증 코드를 확인해야 합니다.
- 전략 평가/로그 검증은 수익성 보증이 아닙니다. 실제 사용 전 모의투자에서 충분히 관찰해야 합니다.

## 기존 설치의 운영 파일 이전

새 버전 디렉터리로 설치하는 경우 운영 상태가 새 디렉터리에서 자동으로 생겨나도록 방치하지 마십시오. 기존 설치에서 새 디렉터리로 이동할 때는 대상 디렉터리에서 다음과 같이 먼저 미리보기 합니다.

```bash
python3 scripts/upgrade_migrate.py --source /path/to/old/kis_auto_trader --destination /path/to/new/kis_auto_trader --dry-run
```

미리보기 결과를 확인한 다음 `--dry-run`을 제거합니다. 대상에 내용이 다른 운영 파일이 있으면 스크립트가 덮어쓰지 않고 중단합니다. 이 경우 파일을 별도 백업하고 주문/잔고 상태를 확인한 후 수동 비교해야 합니다. `cancel_orders.json`의 미확인 주문 기록은 임의로 삭제하거나 합치면 안 됩니다. 원본 설치는 자동 삭제되지 않습니다.


## 관찰 로그와 매매 판정의 구분

`BUILDER_OBSERVE_ALL_STRATEGIES=true`는 `config/strategy_profiles.yaml`에 등록되고 상위 설정에서 활성화된 10개 전략 파일을 관찰·평가합니다. 프로필에서 `decision_enabled=true`인 전략만 프로필의 매수/매도 투표와 가중 점수에 반영됩니다. 관찰 전용 전략의 BUY/SELL은 매매 결정을 직접 바꾸지 않습니다. YAML 내부 `strategy.enabled=false`는 전략 평가를 비활성화하고 점수 분모에서도 제외합니다.

`STRATEGY_SIGNAL_LOG` JSONL에는 종목·전략 ID·전략 파일·BUY/HOLD/SELL/ERROR·조건 평가 사유·데이터 준비 상태·오류를 기록합니다. `__profile__` 레코드에는 매수/매도 점수와 투표 수, 임계값, primary 요건 및 미충족 게이트가 포함됩니다. KIS REST 로그에는 method/path/TR ID/시도 횟수/HTTP·KIS 응답 코드/소요시간이 기록되며, 인증 토큰·App Key·App Secret은 기록하지 않습니다. 보유 종목의 매도 조건 미충족 진단은 종목당 최대 60초에 한 번 INFO 로그로 남깁니다.

재감사에서 공식 강도 계산과 YAML 조건 평가가 서로 덮어쓰는 문제를 수정했습니다. YAML 조건은 최종 BUY/SELL/HOLD를 결정하지만, 프리셋 조건과 일치할 때는 공식 전략 강도를 유지합니다. 회귀 테스트는 모멘텀 매수/매도, 52주 고점, 돌파 실패, 추세 필터 강도와 10개 전략의 진입/청산 사례를 포함합니다.

**알려진 데이터 소스 차이:** 공식 `week52_high` 클래스는 현재가 API의 `w52_high` 값을 사용하지만, V7.0.0 내부 엔진은 공유된 KIS 일봉에서 직전 252거래일 고가를 계산합니다. 이 방식은 260봉 공유 조회를 유지해 추가 현재가 호출을 줄이지만, 공식 API의 52주 고가와 항상 같다고 보장하지 않습니다. 정확한 현재가 API 기준으로 바꾸려면 종목별 추가 REST 호출과 분당 호출 예산을 함께 재검토해야 합니다.

종목 DB는 제공된 `symbol-properties-database.csv`의 equity 행을 그대로 사용합니다. 파일에는 ETF·우선주 등도 포함되어 있어 별도 분류 열 없이 보통주/KOSPI만 추정해 필터링하지 않습니다. 실제 KIS 시세 테스트에서 특정 코드의 데이터가 없으면 해당 항목은 `ERROR`로 남고 테스트 실패로 보고됩니다.
