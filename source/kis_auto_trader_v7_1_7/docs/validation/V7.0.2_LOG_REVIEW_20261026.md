## 검토 범위
- 입력 로그: `kis_auto_trader_v7_0_0_log_20261026.zip`의 trader/error/orders/fills/control/watchdog/strategy_signals/start_request 로그
- 코드 기준: V7.0.1 소스 ZIP을 풀어 확인한 `brokers/kis/client.py`, `brokers/kis/rate_limiter.py`, `trading/orders.py`, `trading/fill_handler.py`, `trading/reconcile.py`, `trading/buy_process.py`, `application.py`, `strategies/builder_engine/official_adapter.py`, `config/strategy_profiles.yaml`

## 1. 체결금액·잔고 정합성

### 확인된 사실
- 첫 거래는 241690 유니테크노 매수 908주 후 매도 908주로 종료됐고, 주문별 개별 체결금액 합산 기준 세전·수수료 전 손익은 약 -40,860원임.
- 두 번째 거래는 매수 920주가 3회 분할체결됐고, 매도 920주는 15회 분할체결됐음. 각 개별 매도 체결금액(`체결가 × 이번 체결수량`) 합계는 로그에 기록된 개별 체결값 기준 3,004,035원임.
- 기존 코드의 `누적체결금액(참고)`는 KIS의 누적 체결금액 필드가 아니라 **마지막 체결가 × 누적 체결수량**으로 계산됨. 따라서 로그에 나온 3,003,800원과 개별 체결 합계 3,004,035원의 235원 차이는 그 자체로 KIS 금액 오류 증거가 아님. 이는 마지막 체결가 × 누적수량이라는 프로그램 참고 계산값과 실제 개별 체결합계의 차이임을 소스에서 확인함. V7.0.2는 이를 실제 누적 체결금액처럼 읽지 않도록 표시를 바꾸고 `FILL_AMOUNT_AUDIT`에 실제 누적금액은 현재 이벤트 구조만으로 알 수 없다고 기록함.
- 시작/종료 잔고 요약에서는 총 평가금액과 예수금/주문가능금액 사이에 불일치가 관찰됨. 종료 시 총 평가금액은 약 9,209,826원, 예수금은 약 9,325,874원, 주문가능금액은 약 9,159,490원으로 로그에 나타남. 원본 KIS 요약 필드와 의미를 확인하지 않은 채 어느 하나를 정답으로 간주하지 않음.

### V7.0.2 진단
- `KIS_BALANCE_AUDIT`: 잔고행 개수, 보유수량/평가금액/매입금액 합계와 선택된 KIS 요약 필드 기록
- `PORTFOLIO_AMOUNT_AUDIT`: 시작/종료 요약의 원본 필드와 화면용 계산값을 함께 기록
- `RECONCILE_BALANCE_AUDIT`: 일일 기준자산 계산에 실제 선택된 필드명을 기록
- `KIS_ORDER_HISTORY_AUDIT`: 당일 주문이력에 제공된 누적수량·금액·평균단가 관련 필드 중 실제 존재하는 필드만 기록
- `RECONCILE_POSITION_AUDIT`: 브로커 종목, 제거 종목, 동기화 후 로컬 수량 기록

## 2. API 호출 제한

### 확인된 사실
- 로그에 `EGW00201` 및 `EGW00215` 호출 제한 응답이 있고, 일부 요청은 HTTP 500으로 전달됨.
- `KisApi` 인스턴스 하나 안에서 REST 요청, REST 토큰 발급, WebSocket approval key 발급은 동일 `self.limiter`를 사용함. 요청 전 호출 제한기 대기와 명시적 제한 응답 뒤 cooldown이 코드에 있음.
- 로그만으로 제한 발생이 동시 호출, 요청 빈도, KIS 서버 정책 중 무엇이 주원인인지는 확정할 수 없음. 별도 프로세스가 같은 앱키를 동시에 사용하는 경우 프로세스 간 제한기는 공유되지 않음.

### V7.0.2 진단
- `KIS_RATE_LIMIT_WAIT`: endpoint, TR ID, 시도 번호, 2초 이상 대기시간, 최근 1초/60초 호출량 기록
- `KIS_RATE_LIMIT_COOLDOWN`: 명시적 제한 코드와 cooldown 기간 기록
- 제한기 정책/요청 재시도 정책은 이번 버전에서 변경하지 않음.

## 3. 후보 출처·전략 판정

### 확인된 사실
- 사용자는 실행 초기에 HTS 조건명을 입력하지 않았고, 이후 공격형 조건명만 입력해 재실행했다고 설명함. 조건명이 비어 있는 시점의 HTS 검색 생략은 설정에 따른 정상 동작임.
- `.env`의 `ENTRY_MODE=ALL`이면 `BuyProcess`는 HTS 후보 점수화 결과를 `run_builder_cycle`에 전달하고, 최종 선택은 Builder 후보를 사용함. 따라서 Builder 로그의 HTS 개수는 원본 HTS 결과행 개수와 같다고 단정하면 안 됨.
- 프로필 파일에서 `enabled`와 `decision_enabled`는 별개임. 프로필 `decision_enabled=true`인 전략만 기본 투표에 참여하며, 각 전략 YAML 내부 `strategy.enabled=false`는 해당 전략을 HOLD/비활성으로 처리함. 모든 전략 YAML을 껐을 경우 매수 투표가 없어질 수 있음.
- 로그의 `hts_condition=7`, `manual_file=0`, `union=3` 표시는 원본/고유 후보 수의 정의가 명확하지 않아 출처 혼동을 유발할 수 있었음.

### V7.0.2 진단
- `[ENTRY_SELECTION_START]`, `[ENTRY_SELECTION_HTS]`, `[ENTRY_SELECTION_BUILDER]`, `[ENTRY_SELECTION_RESULT]`: `ENTRY_MODE`에 따라 실제 어느 결과를 선택했는지와 HTS 후보가 Builder에 전달됐는지 기록
- `[HTS_CONDITION]`: 조건명, seq, 결과행 수, 유효·중복 제거 후 종목 목록 기록
- `[CANDIDATE_SOURCE]`: 각 Builder 종목의 `HTS_SCORED_CANDIDATE`/수동 파일 출처를 분리 기록
- `[STRATEGY_PROFILE_CONFIG_ITEM]`: 전역 등록 enabled, 실제 YAML enabled, 프로필 decision_enabled, weight, primary를 나란히 기록
- `[STRATEGY_DECISION_AUDIT]`: BUY/HOLD/SELL, 점수, 최소 점수, 투표수, primary 여부, 오류 및 실패 게이트 기록

## 4. REST 잔고와 WebSocket 체결통보

### 확인된 사실
- 로그에서 매도 진행 중 로컬 수량과 브로커 수량이 일시적으로 9주 차이 나 브로커 잔고 기준 보정이 발생했고, 이어 REST 잔고가 체결 누적량을 아직 반영하지 않았다는 경고가 반복됨. 최종 종료 시 미체결 주문은 0건이고 보유종목은 없는 것으로 확인됨.
- 기존 코드에는 주문번호/누적체결수량을 이용한 중복 통보 억제와 REST 잔고 선반영 검사 로직이 이미 존재함. 해당 로직을 로그만으로 안전하게 교체할 근거는 부족해 V7.0.2에서는 계산/상태전이 규칙을 바꾸지 않고 판정 경로를 더 자세히 기록함.

### V7.0.2 진단
- `FILL_NOTICE_RECEIVED`: 체결통보의 주문번호, 통보 번호/시각, 개별 수량·가격, 누적수량, 응답에 실제 존재하는 금액 필드 기록
- `FILL_NOTICE_DUPLICATE_SUPPRESSED`: 중복으로 억제한 누적수량과 REST/통보 기준 수량 기록
- 기존 `체결통보 대사`, `잔고 수량 대사 차이`, `REST 잔고가 아직 누적체결을 반영하지 않음` 로그와 함께 시간순으로 확인하도록 구성

## 아직 결론 내리지 않은 항목
1. KIS 잔고 요약 필드 간 의미 차이와 종료 시 평가금액/예수금/주문가능금액 차이의 원인
2. `EGW00201/EGW00215`가 발생한 순간의 전체 동시성/분당 호출 패턴과 외부 프로세스의 앱키 공유 여부
3. 체결통보/주문이력에서 실제 누적 체결금액 필드가 제공되는지, 제공된다면 그 값과 개별 체결합계가 일치하는지
4. WebSocket 재연결 후 모든 가격/체결 구독이 복원됐는지 여부

이 항목들은 V7.0.2의 새 로그가 쌓인 뒤 실제 응답값을 대조해 판단해야 함. 본 버전은 원인을 확인하지 않은 회계·주문 상태 계산 변경을 피함.
